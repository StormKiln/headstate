# 8.2 transcript benchmark — 2026-10-01

Apple M2 Max, macOS 26.6.2, Playwright 1.63.0 Chromium headless shell
153.0.8010.12; 1280×800 viewport. One measured opening per window, fresh
browser context for each window, compiled Vite harness. This is not an app
startup/cold-machine distribution. Twelve production windows generated by
`read_bench::transcript_message_payloads` from the four synthetic fixtures;
actual window sizes are 1–101 messages under the 200-message page cap.
Initial cursors, positions, seam, clipping and I/O metadata are preserved.
Static start/middle cases render their selected page's newest message, not
the newest message of the whole file. Static adjacent paging is refused;
scrolling here traverses the loaded page. Follow/growth use end windows and
explicitly synthetic subsequent pages. No competing builds ran during timing.

Preparation used `BENCH_TRANSCRIPT_OUT=/private/tmp/headstate-82-final-browser`
with `make bench-transcript-browser`, retaining twelve production payloads.
After correcting the driver's legacy message-count access and static fixture
setup, the final run used the same build/fixtures:

```sh
HARNESS_PHASES=open,follow,growth,b5 node scripts/transcript-browser-bench.mjs /private/tmp/headstate-82-final-browser
```

Exit 0. Raw output: `/private/tmp/task10-browser-final.log`. Source fixtures
also remain at `/private/tmp/headstate-82-final-bench-rust`. These are current
production-page measurements, not a relabelling of historical 400-message
stress results. Raw table `MB` heap labels use 1024² bytes (MiB); CDP reports
whole JS heap after forced GC, not transcript-only allocations or process RSS.
The gate's desktop heap threshold is 50 MiB. Native/phone memory acceptance
remains unmeasured. Frame p95 is reported, not gated as a physical 60fps claim.

Opening tasks reached 58ms in this run; they are reported separately from
the zero long tasks during scrolling. B4 idle work is nonzero, including
status updates and harness serialization. This satisfies the explicit
regression checks (no idle row mutation/long task, bounded reads), not a
literal assertion of no CPU work. New-message paint in B4 is double-rAF,
a paint-opportunity proxy distinct from B1's exact Element Timing text entry.
B5 uses historical compression ratios as an estimate, not new on-wire data.
