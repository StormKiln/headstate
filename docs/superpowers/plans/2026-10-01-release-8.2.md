## Task 1: #1100 — PR Stats: read from the store first, so a scope with coverage paints instantly

## What this is

**Stage 4 of #1094**, deliberately deferred when stages 1-3 shipped in
`a049e6a` (v5.23.0). #1094 is closed; this is the remaining stage, filed so it
does not live only in a closed issue's comment.

## The change

`stats_board` currently still **fetches first**. Stage 4 restructures it into:

1. **Read** — assemble from `pr_history` + `pr_slice` for the requested window.
   A SQLite read, sub-millisecond, **zero GitHub requests**. Return it.
2. **Register** — upsert `pr_backfill_scope` with `last_viewed = now`, so the
   worker knows this scope matters.
3. **Nudge** — wake the backfill worker (a `tokio::sync::Notify`, the `waker`
   pattern `poll::spawn` already takes) so a click gets the next tick rather
   than waiting up to `BACKFILL_INTERVAL`.

`stats_board` stops being the thing that fetches. It becomes a store read plus
a registration.

## Why it was deferred, and what must be true before it lands

**This is the only stage that changes what an existing user sees on an existing
scope.** A cold scope would return an empty-but-honest board immediately, where
today it blocks up to 60s and then returns a partial.

That is a regression unless the worker is demonstrably filling the store. So the
precondition is evidence, not code:

> Run v5.23.0 on the large account for a few days and confirm the backfill
> worker is actually converging — `pr_slice` gaining `complete` rows, the
> coverage line advancing, `[diag] backfill` ticks landing within their floor.

If the worker is not converging, stage 4 turns a slow page into a permanently
empty one. If it is, stage 4 is what makes the page paint instantly.

## The mitigation #1094 specifies

Keep **one** foreground load on the first click for a scope with **zero
coverage** — the existing `load_board_accumulating` path, gated on
`permits(board_projection)` as today. So a first click still does what it does
now, and every later improvement comes from the worker.

Do not skip this. Without it, the first view of a new scope is blank.

## Tests

- A scope with stored coverage renders from the store with **zero** GitHub
  requests. Assert on requests issued, not on the answer.
- A scope with zero coverage still performs its one foreground load.
- Clicking a scope registers it in `pr_backfill_scope` and wakes the worker.

## Not in scope

Anything that would make an uncovered range render as a measured zero. The
absent-is-not-zero rule is the one #1094 flags as most likely to break here,
and stages 1-3 built `pr_slice` specifically so a day with no row reads as
uncovered.

## Task 2: #711 — Transport: call<T> asserts response types rather than checking them, and phone/desktop ship independently

`Transport.call<T>(name, args)` is an unconstrained generic. The caller names
the return type, nothing checks it, and `call` is a one-line pass-through
(`src/api/transport.ts:46`). There are **91** `call<…>()` sites in
`src/api/tauri.ts`, and no runtime validation library anywhere in the project.

So every response type in the app is an **assertion, not a check**.

## Where this is nearly harmless

On the desktop, `src-tauri/src/commands.rs` and `src/types/pr.ts` are compiled
from the same commit. A mismatch is a build-time bug someone catches, and
validating those 91 call sites would pay a real cost for a state that cannot
occur.

## Where it is a real, reachable state

The **companion**. The phone and the desktop ship on independent tags
(`docs/mobile-release-process.md`: *"The companion's version is its own …
independent of the desktop's. Compatibility between the two is the wire
protocol's integer version, not either app version."*).

`PROTOCOL_VERSION` is bumped for deliberate surface changes. Adding a field to
a response is backward-compatible and correctly does **not** bump it. So a
phone built after a feature, paired to a desktop built before it, is a
legitimate protocol-2-to-protocol-2 pairing that receives a response missing
those fields — and with two release pipelines that ordering is ordinary rather
than exotic.

A `T` claiming the fields are present is then a false guarantee. It surfaces as
`undefined` at a property access, far from the command that produced it, rather
than as an error naming what came back wrong.

## How this surfaced

#710 added three fields to `Footprint`. I asked for them to be typed as
required, reasoning that version negotiation would refuse an older desktop. It
does not: `companion.rs:290` guards the version check with
`matches!(class, Class::Write | Class::Destructive)`, and `system_footprint`
is `Class::Read` — **reads bypass the gate entirely**. They stayed optional,
correctly.

But the deeper point is that the type would have been a lie either way. Even
where a shape mismatch is genuinely unreachable, `call<T>` cannot enforce it.

## Scope — the useful framing

**Do not validate all 91 uniformly.** Most are desktop-local and would pay for
a mismatch that cannot happen. The set worth validating is the commands
reachable over the remote surface — the `Class::Read` entries in
`src-mobile/src/surface.rs` that the phone actually calls. That is a much
smaller list, and it is exactly where version skew makes a shape difference
real.

Worth deciding deliberately:

- **A validation library** (zod and friends) means a schema per remote command
  and a new dependency in the supply chain, which this repo audits with
  `cargo deny` on the Rust side and takes seriously.
- **Hand-written guards** for the remote set only: no dependency, more code,
  and a second place to keep in step with `types/pr.ts`.
- **Nothing, deliberately**, on the grounds that missing fields render as
  "Not measured" anyway. That is defensible for optional display data and NOT
  defensible for anything a decision is made from.

## Done when

A response over the remote surface whose shape does not match what the phone
expects produces an error naming the command, rather than an `undefined` that
appears somewhere else later.

## Task 3: #1530 — Since-you-left: store the marker's cursor so a far-back marker can be opened

Follow-up from 7.9 (#1484, PR #1517).

## Problem
The "since you left" marker stores a message id. For a marker far back in a long session, the follower calls `seek(id, null)` (`src/lib/transcriptFollow.ts`). Without a cursor, `seek` can only find the id by paging backwards, so it is bounded by what can be held (about 2,000 messages). A marker further back than that cannot be opened.

## Proposed
Store the marker's record **cursor** (offset plus behind-digest, as pages already carry) alongside the id. `seek` can then read the page at the marker directly. If the cursor is stale because the file was rewritten, fall back to the current behaviour and say so.

## Task 10: #1487 — Transcript performance and memory budgets, with fixtures and a measuring harness (gates the virtualization choice)

## Goal

Set explicit performance and memory budgets for the transcript viewer, with a harness that measures them, so virtualization and follow decisions are made on numbers.

## Fixtures
Generated, generic content, shaped like real sessions:
- a 1,000-message session;
- a 10,000-message session;
- a 70 MB tool-heavy transcript (the real corpus has 14 files over 8 MB, the largest 73.2 MB, per #1220);

## Budgets
Starting points, to be confirmed on hardware:
- **Open to first paint at the newest message:** desktop < 300 ms, phone < 800 ms on the LAN.
- **Scrolling:** no long tasks > 50 ms while scrolling. 60 fps target on desktop and the phone (iPhone 12-class).
- **Resident transcript memory:** desktop < 50 MB, phone < 25 MB, regardless of transcript size.
- **Live follow:** idle follow costs no main-thread work beyond one stat per tick. Growth costs O(new bytes).

- A Rust benchmark for the paging reads, with a reverse page at the start of a 70 MB file.
- A browser-level test (Playwright against the Vite build, or the existing Chrome tooling) that opens each fixture and records first paint, long tasks during a scripted scroll, and the JS heap.
- A manual phone checklist with Instruments (Allocations, Time Profiler) until the phone can be automated.
- Results are recorded in the PRs. Regressions over budget fail the harness.

- The memory window in the live-follow issue.

## Task 11: #1626 — Dense-day backfill convergence

Execute immediately after Task2 and before the remaining transcript tasks. This is a prerequisite for Task1 release acceptance, discovered from public worker code during validation.

## Problem

A merged-PR day larger than one detail page can remain incomplete indefinitely while background ticks repeat the same first page. This blocks reliable store-first PR Stats (#1100) and spends requests without filling coverage. A worker tick can also label the scope converged while its final selected days are still incomplete.

## Code diagnosis

- `src-tauri/src/poll.rs` selects the first `GROUP_SLICES` uncovered days on every tick and calls `github::stats::fetch::load_detail_chunked`.
- That detail loader starts with `SLICE_PAGE_FULL` (50 nodes) and uses the existing degradation ladder. It does not continue a dense day's search cursor across ticks.
- `backfill::classify` correctly keeps a short day unsettled. The next tick therefore chooses that day again and fetches its initial nodes again. Several dense early days can starve later days in the same scope.
- The tick's final `Complete` decision uses the pre-fetch uncovered-day count relative to the selected group size, rather than checking whether the stored coverage actually settled. A final dense/refused day can therefore be reported as converged.

## Acceptance

1. A synthetic day with 120 distinct PRs converges over bounded background work; subsequent completed ticks issue no requests.
2. Persist progress safely across ticks/restarts, or use an equivalently bounded strategy that does not repeatedly fetch an unchanged initial page.
3. Scope/account identity, query window and measure isolate progress. Partial results remain available; missing, refused, changed or malformed pages never become complete coverage.
4. Keep the background rate floor, per-tick request budget, sequential cadence, foreground priority and cancellation behavior. Dense days must not indefinitely starve other days/scopes.
5. Report converged only when stored coverage is actually complete; truncated/refused days remain working or explicitly stalled.
6. Exercise the actual worker path with a cursor-aware synthetic server, restart/resume, duplicate/repeated cursor, refusal, budget and final-coverage regressions.

Discovered during 8.2 implementation. All reproduction fixtures and public evidence must use synthetic repositories and counts; no private diagnostic contents belong here. Include in #1625 before enabling store-first Stats.
