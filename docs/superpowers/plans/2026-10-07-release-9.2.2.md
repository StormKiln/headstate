# Headstate 9.2.2 implementation plan

**Goal:** Release all fixes from the 9.2.1 enterprise approval diagnosis as desktop 9.2.2 and the compatible shared-frontend companion.

**Specification:** GitHub epic #1751 and issues #1744–#1748, #1750; the user authorized implementation, merge and release. Field acceptance #1737 remains owner-run after release.

**Architecture:** Preserve the existing provider/account/principal identities and evidence lifetimes. Give explicitly selected action prerequisites bounded foreground admission; keep list enrichment advisory. Successful post-approval reads must reconcile through the same acceptance fences as ordinary detail reads, with separate local recovery state instead of claiming GitHub is checking when no usable read arrived. Logs contain fixed categories and counts, never company identifiers.

**Stack:** React/TanStack Query/TypeScript; Tauri/Rust/Tokio; existing GitHub Actions desktop and companion release pipelines.

## Constraints and acceptance

- Retain synthetic data and loaded content; preserve drafts and expanded comments.
- No merge from stale, unknown or mismatched head/base evidence. Preserve native-stack routing.
- Respect provider cooldowns, original deadlines, single recovery probe, cancellation and principal retirement.
- Do not increase global concurrency or make every list row foreground work.
- Current-head review acknowledgement survives provider read lag; old account/head/source results cannot overwrite newer state.
- Deterministic tests must assert action usability and actual request counts under 150+ PR load and exhausted advisory credit.
- Test first; focused red/green evidence per task, integrated full suites and independent review before merge.
- Audit all CI attempts before tagging; no force, deleted tags or bypassed release gates.

## Review focus

1. 150+ PR inventory and exhausted advisory budget: selected action remains able to acquire fresh evidence, list traffic stays bounded.
2. Newer account/head/base or retired mobile principal during an in-flight request: old answer never regains authority.
3. Approval succeeds but readback fails or provider returns pending: receipt/content retained and truthful recovery state, no stale Merge enablement.
4. Native publication arrives before detail command returns: matching successful read does not cause a redundant full read; genuinely newer data still gets a bounded catch-up.
5. Cancellation/timeout and probe completion races: no leaked permits, lost wakeups, concurrent probes or shortened provider deadlines.
