# Headstate 8.2.1 review reliability

## Intent and authorization

The user requests a deep parallel diagnosis, issues for all discovered work, and an immediate follow-on release for large-organization To Review failures. 8.2.0 has already shipped; this patch targets v8.2.1. User-facing success is stable usable cached review inventory and detail, dependable approval feedback, bounded provider work, and eventual convergence after transient failures. This is a coordinated repair of existing interfaces, not a replacement sync engine. The user already authorized landing the follow-on work; no separate permission pause is required.

Private diagnostics remain outside the repository. Public issue evidence uses source at 13458e2 and synthetic cases. The diagnosed session supports successful actions followed by failed reads, but does not prove every reported approval error was a provider write rejection. All ten work items are linked under #1632 (#1633–#1642).

## Chosen approach

Keep the existing source receipt coordinator, SQLite cache, query hooks and provider clients. Extend their evidence and bounded scheduling where the concrete defects cross those boundaries. UI-only retention would leave durable list deletion and provider overload; larger timeouts/caps would amplify contention. The selected layered repair preserves good data, treats unknown as unknown, limits background work, and reconciles actions against authoritative evidence.

### Inventory and readiness

A failed request never deletes usable inventory. An incomplete successful enumeration updates observed valid rows but retains unseen rows with explicit last-known provenance. Reconciliation occurs before persistence/publication, so desktop, paired phone and restart agree. New rows with unread readiness fields cannot become affirmative Ready entries. Previously known Ready rows remain visible with qualification during partial failure rather than disappearing merely because they were unobserved. A changed head cannot inherit a fresh verdict from an old head. Existing account/source/list/generation barriers remain authoritative; explicit confirmed removals and actions must not be resurrected by stale rows. GitHub currently lacks a persisted confirmed-effect bridge, so add one before enabling retention: patch committed inventories and retire pre-effect generations, then apply scoped effects during reconciliation. Retained union size must never replace newly observed cardinality in shortfall/coverage arithmetic.

Carry minimal optional typed row evidence in the existing PR/wire model, with old successful payload compatibility. Use shared RowObservation with observed/retained state, actual optional last-observed timestamp, and disjoint closed unknown/retained readiness-field sets (draft, CI, merge, review, queue). Reuse known fields only on the same established head; an unread head preserves last-known identity or unknown qualification, never silently transfers evidence. A positively changed head stays visible in inventory but loses affirmative Ready until measured. Do not transmit provider error text as evidence. Coverage accumulates partial errors, unknown totals and conflicting totals across all pages; contradictory evidence never authorizes deletion or a confirmed denominator. Completed consistent enumeration or explicit confirmed removal can retire unseen IDs. Mixed-time page counts alone cannot establish an atomic snapshot; conservative retention must be qualified and eventually reconciled.

### Bounded scan progress

Do not raise the old ten-page cap and repeatedly refetch the same rich prefix. Maintain a per-client/source/query scan continuation with bounded request/deadline work and fair retries. Keep successful accumulated inventory and advance late work even when early rows change. Account/query changes discard incompatible continuation. Respect the provider search ceiling; beyond it use bounded partitioning if trustworthy, otherwise expose incomplete coverage and never falsely converge. Repeated static inventories beyond 250 must enumerate every ID. Cached warm mounts/reorders do not trigger whole-list scans. Persist progress if needed for restart guarantees; keep SQLite migration and source ownership explicit.

### Request admission, cooldown and cache

Use client/account-owned shared read admission; reserve foreground capacity rather than putting selected detail/actions behind an unbounded advisory FIFO. Initial target: at most four in-flight GitHub reads, at most two background/advisory reads; explicit foreground detail is not blocked solely by those two. Writes retain their separate bounded, non-retrying semantics. Do not evade a known applicable provider retry deadline; a refusal before dispatch is distinguishable from unknown write outcome.

Ready enrichment gets a shared finite actual-attempt budget: initially eight supporting HTTP attempts per 30-second client cycle, including retries, with at most two active advisory reads. An advisory command must return completed rows/qualified deferrals within ten seconds, below the remote envelope. Cancellation must release permits and leave no detached retry worker. Warm same-key/reordered/multi-window reads coalesce and reuse fresh receipts. Fair eligibility advances past unreadable prefixes. Stack/rules/pusher caches are bounded and client-owned; keys include actual branch/head/base inputs. Evict incrementally rather than clearing the whole map. Ordinary viewer lookup uses the successful per-client initializer and retries failures safely.

Retain rate-limit bucket, remaining and reset evidence under client ownership. A known elapsed reset or cooldown permits one coordinated recovery probe; do not release a herd or let a stale response overwrite a newer reset window. Unknown headers remain unknown. REST reserve refusal must recover without restart. Handle numeric/date Retry-After and do not classify ordinary authorization403 as throttling. All limits count actual transport attempts, not batch rows.

### Detail and actions

A successfully fetched detail remains mounted after timer/focus/manual refetch failure, with an inline warning and retained external navigation. Cold failure and row-only placeholder are not full successful detail. Optional ancestry does not delay primary detail. Failed/timed-out check continuations preserve validated first-page data with explicit partial/unknown check qualification and honest totals; denied access never becomes fabricated success. Stack metadata can arrive separately under the same bounded advisory policy.

Read staleness alone must not permanently disable approval of content the user actually viewed. Bind a submitted review to that viewed head using the provider-supported commit identity; reject/refuse safely when identity is absent, the server reports mismatch, or an applicable provider cooldown prevents dispatch. Do not require a successful advisory refresh as a prerequisite. Destructive merge facts still require their existing safe guards. GitHub official schema confirms AddPullRequestReviewInput.commitOID and review receipt commit/id/state/submittedAt; GitLab approval supports sha matching HEAD (https://docs.gitlab.com/api/merge_request_approvals/).

Confirmed review receipts survive lagging ordinary reads for the same account/PR/head. Reconciliation can retire them on authoritative newer head/review/dismissal evidence; never pin approval indefinitely. Unknown write outcome has a visible check-first state, distinct from a definite rejection or verified success, shared by relevant controls/observers. No automatic mutation replay. Missing/null review receipt is not success, and diagnostics distinguish a transport response from semantic confirmation. Do not introduce review-body logging.

### GitLab and shared frontend

GitLab uses the same inventory/UX truths, while its existing process transport gains bounded foreground service and retained retry deadlines. A failed GitLab source cannot degrade healthy GitHub rows. GitHub-only mode starts no GitLab work. Preserve host/account ownership, native subprocess bounds and no write replay. No new transport architecture or live synthetic-data deletion is part of this patch.
