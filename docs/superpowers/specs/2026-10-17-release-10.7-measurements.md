# HeadState 10.7 SQLite measurements

Synthetic fixtures only, using application-linked SQLite 3.53.2 through Rust tests. Local debug test build; elapsed times are observations, not production promises or CI timing thresholds. Each variant uses a fresh temporary WAL database, auto-checkpoint disabled and WAL truncated after seeding. No personal database or transcript was opened.

## FTS identity (#1852)

Run: `cargo test --manifest-path src-tauri/Cargo.toml --lib store::sqlite_efficiency -- --include-ignored --nocapture`.

Corpus bodies contain repeated synthetic text. The batch replaces 100 sessions inside one immediate transaction; this isolates identity cost and includes mapping writes, but is not a full population-pass benchmark. Production per-session transaction/fence behavior is unchanged.

| Sessions | Lookup VM steps before / after | Batch writer time before / after (ms) | WAL bytes before / after |
|---|---:|---:|---:|
| 1,000 | 3,011 / 13 | 39.392 / 8.790 | 354,352 / 387,312 |
| 10,000 | 30,011 / 13 | 517.740 / 15.611 | 1,652,152 / 1,911,712 |
| 50,000 | 150,011 / 13 | 2,675.741 / 38.227 | 5,413,712 / 5,755,672 |

The mapping removes corpus-sized identity scans. It adds storage and WAL writes (about 6–16% more WAL for these batches); it is a writer-time improvement, not a claim that all write bytes decrease. The regression asserts bounded VM work and use of the session index, not these timings. Existing duplicate and NULL identities are retained by migration; successful authoritative reindex normalizes only that session. Unchanged sessions retain the existing no-reindex behavior.

## Session/run ordering (#1853)

Run: `cargo test --manifest-path src-tauri/Cargo.toml --lib session_sort_measurements -- --ignored --nocapture`.

Each fixture has three runs per session, NULL activity on one quarter of sessions, activity ties, and full production SELECT columns. Both queries change from one temporary sort each to zero. Run grouping uses the existing `(session_id, started_at DESC)` index; no new run index is added. Session index includes `first_seen_at DESC` and replaces the shorter index.

| Sessions | Session VM before / after | Run VM before / after | Combined read ms before / after | Database bytes before / after |
|---|---:|---:|---:|---:|
| 1,000 | 27,759 / 12,008 | 51,009 / 24,008 | 2.311 / 1.721 | 856,064 / 880,640 |
| 10,000 | 277,509 / 120,008 | 510,009 / 240,008 | 26.251 / 20.790 | 5,943,296 / 6,209,536 |
| 50,000 | 1,387,509 / 600,008 | 2,550,009 / 1,200,008 | 165.458 / 157.997 | 29,511,680 / 30,674,944 |

Appending 100 sessions plus 300 runs took 3.451/3.503/3.450 ms before and 3.332/3.631/3.521 ms after at the three sizes. WAL bytes were 164,832/284,312/276,072 before and 193,672/333,752/383,192 after. The composite index trades additional storage/write bytes for avoiding sorts; list materialization still reads all rows and is not claimed constant-time. Cross-session evidence remains available and NULL/tie/per-session newest ordering is covered by production-query tests.

## Per-source checkpoint persistence (#1879)

## Synthetic measurements (debug build, bundled SQLite)

32 synthetic sources, each retaining 1,024 SHA256 block digests (4MiB accepted history) and a 64KiB partial record. Append one byte to one checkpoint. No user transcripts or databases used. Timing is an observation, not a CI limit.

| Metric | Whole legacy cursor | One changed source |
|---|---:|---:|
| Serialized JSON bytes | 10,597,354 | 331,103 |
| Serialization microseconds | 336,370 | 10,264 |
| Production-shaped UPSERT VM steps | 26 | 28 |
| Row mutations | 1 | 1 |
| Transaction microseconds (serialization excluded) | 41,370 | 1,007 |
| WAL bytes after TRUNCATE baseline | 10,687,312 | 341,992 |
| Allocated DB bytes after update | 21,520,384 | 21,532,672 |
| Live DB page bytes (allocated minus freelist) | 10,915,840 | 10,928,128 |

This is about 32x less serialized data and 31x less WAL for one changed source. VM opcode counts are nearly identical because large SQLite values amplify byte I/O without proportional VM instructions. The per-source format adds pages/row overhead; it is a write-amplification improvement, not database compaction. Migration retains freed pages for reuse; no VACUUM/checkpoint lifecycle policy was introduced.

Memory was measured as exact owned payload buffer capacities, not RSS: total legacy checkpoint hash/partial-record heap 4,980,736 bytes; changed source hash/partial heap 221,184 bytes (its Vec capacity doubled after append). These counts include String entries in the hashes Vec plus allocated hash strings and line buffers; exclude BTreeMap/path/container overhead, allocator bookkeeping and SQLite. Original unchanged per-source payload heap is 155,648 bytes. New runtime does not retain all decoded checkpoint payloads; it retains membership, one current source and staged changed JSON. Original/checkpoint/parser rollback copies can transiently coexist (up to three copies per processed source).

A separate long-partial fixture: 1,048,576 raw bytes => 4,194,646 JSON bytes, with 1,048,576 known payload heap bytes. Existing numeric-array JSON is deliberately unchanged, exposing its real amplification. Digests alone occupy 65,536 hex characters per 4 MiB source history; binary digest values would need 32,768 bytes before container encoding. Binary checksums were not introduced: they would require a new strict representation/migration contract, and this patch obtains changed-source isolation without altering continuity evidence.

## Residual proportional limits / follow-up evidence

- Storage remains O(accepted source history / 4096) digests plus bounded per-source partial/parser state. No unresolved evidence is evicted.
- Path/offset membership is O(number of sources). Warm payload decoding and equality remain O(payload); zero transcript body reads is not zero CPU/database reading.
- A growing single source rewrites its entire own checkpoint. One large partial record or long source can still be expensive.
- Staged serialized strings consume O(sum of changed source payload sizes), not a global constant. The 16 MiB transcript-read budget does not cap serialization: small changes to many long-history sources can stage large payloads. In this fixture all 32 changed sources would stage about 10.6 MB. Root agreed this becomes a follow-up under sustained-performance epic1851 rather than inventing an evidence-retention/fairness policy here.
- One-time migration necessarily strictly parses the complete legacy cursor and writes all source rows atomically. Malformed legacy state is an explicit failure, never silently treated as absent.


Residual staging and single-source serialization work is tracked in #1890 under #1851.
