# Advisory continuation and detail evidence

`get_ready_pushers(rows)` keeps its request and array response shapes on desktop IPC and the paired/mobile remote surface. Every accepted input row has a response row, including rows not dispatched before the shared deadline. A later call with the same logical membership continues after the last actual dispatch, even when that dispatch was canceled before an answer. Input order and head changes do not create a new batch; adding or removing members does. New membership begins from the existing per-identity opportunity history.

The authenticated native client admits at most 512 recent multirow batch contexts. Each context stores a SHA-256 membership digest and one cursor. Contexts idle for five minutes can retire, unless an executing call still holds a lease. A new distinct batch at capacity receives an actionable command error before any provider request. Retry that batch after idle contexts retire; do not interpret this error as an empty result or permanently discard its tail. Repeating an admitted batch refreshes its lifetime. Same-membership concurrent callers share the context. Singleton callers (the current Ready UI) do not allocate batch contexts. This admission bound replaces implicit eviction starvation with explicit backpressure; it does not change the shared eight-attempt window or four-total/two-background provider concurrency.

Within an admitted, repeatedly demanded finite batch, cyclic ordering gives every member a dispatch opportunity as shared admission allows. Admission denial, account retirement and more than five idle minutes may restart scheduling progress. Useful rules, pusher and stack value caches are independent and remain intact. An unbounded sequence of novel memberships cannot demand unbounded retained scheduling state.

`get_review_gates` adds optional `rules_valid_for_ms` and `pusher_valid_for_ms`. They are original remaining native receipt lifetimes, read atomically with each value. Successful policy and pusher receipts remain 600 and 60 seconds; inconclusive cache entries remain five seconds. The independent pusher stage consumes the policy's remaining lifetime, and cannot erase a successful rules result. Older desktops omit these fields; new frontends suppress current authority for such replies. The shared frontend consumes command transit time conservatively and expires policy and pusher guidance independently, even while replacement work is pending.

Only the selected detail observer revalidates, at original success expiry or a minimum 30-second recovery cadence. Hidden views do not initiate periodic reads. Explicit Refresh coalesces active primary and gate reads, and native caches/admission still govern provider work. Account, source-generation and pairing retirement fence late completions. Desktop and mobile render the same frontend; the generated remote validator accepts older replies and validates the additive lifetime fields.
